# Design

## Context

Модуль `bills` (`src/bills/`) наразі підтримує лише `POST /bills` (створення) і `POST /bills/:id/pay` (оплата за `id`). Response-типи — прості `interface` з ручним мапінгом Prisma-моделі (`amount.toNumber()` тощо), без `class-transformer`/`ClassSerializerInterceptor`. У проєкті немає жодного спільного механізму пагінації (`common/`, `shared/` відсутні) і немає auth/`userId` — список буде глобальним, без прив'язки до користувача. Сховище — Prisma з better-sqlite3-адаптером (`src/prisma/prisma.service.ts`). Мотивацію див. `proposal.md — Why`.

## Goals / Non-Goals

**Goals:**
- Offset-пагінація (`page`/`limit`) з дефолтами й межами (`page=1`, `limit=20`, максимум `limit=100`).
- Фіксоване сортування `createdAt DESC`, без параметра сортування.
- Response envelope `{ data, meta: { total, page, limit, totalPages } }`.
- Валідація параметрів пагінації через існуючий глобальний `ValidationPipe` (той самий підхід, що й у `CreateBillDto`).

**Non-Goals:**
- Cursor-based пагінація.
- Фільтрація, пошук, кастомне сортування — окрема майбутня фіча.
- Reusable/generic pagination-інфраструктура (`common/`-модуль) — передчасно, поки є лише один список-ендпоінт.
- Прив'язка списку до користувача (auth у проєкті відсутній).

## Decisions

**1. Offset-based пагінація (`page`/`limit`) замість cursor-based.**
Обрано за прямою вимогою й простотою реалізації для UI-списку. Cursor-based краще масштабується і не має проблеми "зсуву сторінки" при паралельних вставках, але це надмірна складність для поточного обсягу даних (SQLite, без підтвердженого навантаження). Ризик зсуву сторінки прийнятний — див. Risks.

**2. Локальний `GetBillsQueryDto`/`PaginatedBillsResponse` у `src/bills/`, а не спільна pagination-інфраструктура.**
У проєкті ще немає жодного іншого списочного ендпоінта, тож виносити `PaginationQueryDto`/`PaginatedResponse<T>` у `common/`/`shared/` зараз — передчасна абстракція (YAGNI). Коли зʼявиться другий список-ендпоінт, узагальнення варто зробити окремою зміною на основі двох реальних використань.

**3. `GetBillsQueryDto` як клас з `@Type(() => Number)` (class-transformer) + `class-validator`, а не `ParseIntPipe`/`DefaultValuePipe` на рівні параметрів контролера.**
Зберігає єдиний підхід до валідації вхідних даних, що вже використовується для `CreateBillDto` (DTO-клас, а не per-param pipe'и). Дає безкоштовно `whitelist`/`forbidNonWhitelisted` і для query — сторонні query-параметри відхиляються так само, як зараз сторонні поля тіла запиту в `POST /bills`. Дефолти (`page=1`, `limit=20`) виражаються через ініціалізатори полів класу; це сумісно з `strictPropertyInitialization: false` у `tsconfig.json`, додаткових послаблень strict-режиму не потрібно.

**4. `this.prisma.$transaction([bill.findMany(...), bill.count()])` (array-форма) для одночасного отримання сторінки й загальної кількості.**
Атомарність потрібна, щоб `data` і `meta.total`/`meta.totalPages` не розійшлися, якщо між двома окремими запитами відбудеться паралельний `create`/`pay`. Array-форма `$transaction` виконує обидва читальні запити в межах однієї транзакції без додаткової конфігурації (той самий `PrismaService`, що й у наявних методах).

**5. Мапінг `Bill` → `BillResponse` виноситься в приватний метод `BillsService.toBillResponse`.**
Наразі ідентичний блок мапінгу дублюється в `create` і `pay`; додавання третього входження в `findAll` — природна точка для виділення хелпера. Ізольований рефакторинг, що не змінює поведінку (наявні unit/e2e тести для `create`/`pay` лишаються зеленими без модифікацій).

**6. Фіксоване сортування без параметра.**
Пряма вимога користувача; параметризоване сортування — явно названа майбутня фіча, не проєктується наперед.

## Risks / Trade-offs

- **Зсув сторінки при offset-пагінації**: якщо між запитами двох сторінок відбувається вставка/видалення рахунку, елементи можуть зміститися між сторінками або повторитися. Некритично для поточного use case (немає concurrent multi-user навантаження, немає auth); прийнятний trade-off заради простоти. Мітигація в майбутньому — перехід на cursor-based пагінацію, якщо зʼявиться потреба.
- **Відсутність верхньої межі на `total`**: не проблема для очікуваних обсягів SQLite-бази в цьому проєкті.
