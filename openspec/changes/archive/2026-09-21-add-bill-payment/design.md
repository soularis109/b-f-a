# Design

## Context

Персистентність — Prisma + SQLite (`@prisma/adapter-better-sqlite3`), один Node-процес, синхронний нативний драйвер під асинхронним Prisma API. `Bill.status` наразі типізовано Prisma-переліком `BillStatus`, який містить лише `unpaid` (`prisma/schema.prisma`). `BillsService.create` — єдиний існуючий метод сервісу; `BillsController` — єдиний існуючий ендпоінт (`POST /bills`, стандартний Nest-код `201`). У кодбазі відсутній будь-який `HttpException`-нащадок (`NotFoundException`, `ConflictException` тощо) і відсутній глобальний exception filter (`src/setup-app.ts` реєструє лише `ValidationPipe`). Детальніше — proposal.md.

## Goals / Non-Goals

**Goals:**
- Додати перехід стану `unpaid → paid` через `POST /bills/:id/pay`.
- Гарантувати, що повторний виклик на вже оплаченому рахунку не змінює стан і повертає зрозумілу помилку.
- Встановити перший прецедент обробки помилок (`NotFoundException`/`ConflictException`) для решти модуля.

**Non-Goals:**
- Не вводити окрему сутність/таблицю `Payment` чи лог платежів — «немає повторного платежу» реалізується як заборона повторного переходу статусу, не як унікальний запис.
- Не додавати нове поле `paidAt` — час оплати покривається наявним `updatedAt` (Prisma `@updatedAt`, оновлюється автоматично при будь-якій зміні рядка).
- Не додавати валідацію формату `id` (напр. `ParseUUIDPipe`) — у кодбазі немає такого прецеденту; невалідний/сторонній id природно потрапляє в гілку 404.
- Не змінювати `BillsModule` (providers/controllers/exports).

## Decisions

### 1. Розширення Prisma-переліку замість нової моделі
`enum BillStatus { unpaid paid }` у `prisma/schema.prisma` + нова міграція (`prisma:migrate:dev`). SQLite не накладає CHECK-обмеження на значення переліку (стовпець фізично `TEXT NOT NULL DEFAULT 'unpaid'`), тож для наявних рядків зі статусом `unpaid` міграція даних не потрібна — файл міграції може бути порожнім, але його все одно required закомітити, щоб `prisma migrate deploy`/`prisma migrate status` не бачили дрейфу схеми. Клієнт Prisma (`src/generated/prisma`, у `.gitignore`) необхідно перегенерувати (`pnpm prisma:generate`, також відбувається автоматично під час `prisma migrate dev`), інакше тип `BillStatus` не міститиме `'paid'` і код не типоперевіриться.

### 2. `findUnique` + перевірка статусу + `update`, а не умовний `updateMany`
Альтернатива — `updateMany({ where: { id, status: 'unpaid' } })` і перевірка `count`. Обрано простіший підхід «прочитати → перевірити → оновити»:
- `updateMany` не повертає оновлений рядок, тож для формування відповіді все одно знадобиться додатковий запит — кількість round-trip'ів до БД однакова (2) в happy path для обох підходів.
- `count === 0` з `updateMany` сам по собі не розрізняє «рахунку не існує» (404) від «рахунок вже оплачено» (409) — знадобився б ще один запит для дизамбігуації, тобто `updateMany`-підхід програє за кількістю запитів на error path.
- TOCTOU-вікно між `findUnique` і `update` визнано незначним: один Node-процес, синхронний better-sqlite3-драйвер під Prisma; конкурентний доступ з іншого процесу до цього SQLite-файлу не є сценарієм використання.

### 3. `200 OK` замість дефолтного `201 Created`
`POST /bills/:id/pay` — явний `@HttpCode(HttpStatus.OK)`. Nest за замовчуванням повертає `201` для POST-хендлерів (як і `POST /bills` для створення), але цей ендпоінт виконує перехід стану наявного ресурсу, а не створення нового — тому `200` семантично коректніше. Свідоме відхилення від дефолту сусіднього ендпоінта.

### 4. Немає тіла запиту / DTO
Увесь стан запиту — в URL-параметрі `id`; `@Body()` не оголошується. Наслідок: глобальний `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true })` не спрацьовує на тіло запиту цього ендпоінта — випадково надісланий body мовчки ігнорується, а не відхиляється з `400`. Це прийнятна, свідома поведінка для ендпоінта без корисного навантаження.

### 5. Формат помилок
Перше використання `NotFoundException`/`ConflictException` у кодбазі — стандартна поведінка NestJS (JSON-тіло `{ statusCode, message, error }`), без додавання власного exception filter. Повідомлення: `Bill with id "${id}" not found` / `Bill with id "${id}" is already paid` — встановлює конвенцію для майбутніх помилок у модулі.

## Risks / Trade-offs

- **[Ризик]** Неідемпотентна поведінка: повторний виклик `pay` на вже оплаченому рахунку повертає `409`, а не тихий `200` з поточним станом. Деякі API трактують «оплатити, якщо ще не оплачено» як ідемпотентну операцію (200 при повторі). → **Пом'якшення**: свідомо обрано `409`, бо це прямо відповідає вимозі користувача «повторна спроба... має повертати зрозумілу помилку»; альтернатива розглянута й відхилена.
- **[Ризик]** Дуже вузьке TOCTOU-вікно між `findUnique` і `update` за наявності конкурентних запитів у межах одного процесу. → **Пом'якшення**: визнано прийнятним для поточного обсягу (single-process SQLite); за потреби згодом можна перейти на умовний `updateMany` без зміни зовнішньої поведінки/спеки.
- **[Ризик]** Незакомічена/забута Prisma-міграція призведе до дрейфу схеми в CI/production. → **Пом'якшення**: явний task на генерацію й коміт файлу міграції навіть якщо SQL-вміст порожній.

Послаблення TS strict-налаштувань не потрібне для цієї зміни.
